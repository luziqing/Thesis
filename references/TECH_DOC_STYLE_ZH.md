## 一、规则优先级与三技能分工

冲突时按以下顺序处理，不得为短句、确定语气或格式统一牺牲更高优先级：

1. 保留事实、逻辑、限制、安全信息和法律含义
2. 服从用户明确要求和目标项目约定
3. 保持技术术语和机器可读内容准确
4. 改善结构、语义、语气和可扫读性
5. 最后处理标点、留白、大小写等排版细节

三技能分工（组合使用时先定内容，再清语言，最后排版）：

| 技能 | 负责范围 |
| --- | --- |
| `anti-defensive-writing` | 论文叙事、贡献与证据组织 |
| `de-ai-chinese-writing` | 句式、套话和 AI 腔扫描 |
| `tech-doc-style-chinese` | 中文正文排版：中西文间距、数字与单位、全半角、标点、引号、大小写、链接边界、段落换行 |

论文以期刊或学校模板优先；Word/PDF 页面布局由文档工具处理。自动扫描命中只是复核提示，不构成覆盖排版规则的理由。

## 二、事实保真

- 不新增原文或可靠上下文没有的日期、数字、时限、SLA、能力、条件、因果或结论
- 不删除前置条件、适用范围、例外、风险、警告、兼容性或失败处理
- 不把可能、计划、建议、通常等不确定表达改成确定事实
- 信息不足时保留原意或标记「待确认」，不自行补全
- 引用、法规、合同、错误原文优先保持原文，建议单独列出

示例：

- `截止 4 月 12 日` → `截至 4 月 12 日`
- `尽快处理` → `在约定时限内处理〔具体时限待确认〕`
- 不要凭空补成 `截至 2026 年 4 月 12 日` 或 `30 分钟内处理`

## 三、任务模式

| 模式 | 要点 |
| --- | --- |
| 撰写 | 先定受众、内容类型、事实来源、载体和篇幅；缺关键事实先标记缺口 |
| 改写 | 保留事实、逻辑、层级、限制；默认交付完整改写稿，重大选择另行说明 |
| 校对 | 只处理约定范围内的错字、标点、留白、大小写、术语一致性 |
| 审阅 | 先列问题再给建议，按影响排序并引用原文；未经授权不改文件 |

## 四、语义与语气

- 准确先于修辞，清晰先于热闹；使用克制、直接、可执行的中文
- 优先说明「是什么、适用于什么、需要做什么、接着看哪里」
- 避免问候式开场、宣传口号、空泛形容、连续堆叠黑话
- 默认不直接称呼读者；必要时用明确角色（开发者、实施人员等）
- 一个段落一个主要信息点；一个句子一个清晰主干
- 指代可能不清时，用具体名称替代「该」「其」「此」「上述」
- 标题反映用途，不只使用抽象名词；删除重复信息但不删事实、条件和例外

## 五、术语与排版

### 中西文留白（盘古之白）

可见正文中，中文与英文、缩写、阿拉伯数字、版本号之间加一个半角空格：

| 不推荐 | 推荐 |
| --- | --- |
| `使用API获取数据` | `使用 API 获取数据` |
| `等待3秒` | `等待 3 秒` |
| `版本2.0已发布` | `版本 2.0 已发布` |
| ``运行`npm install`安装依赖`` | ``运行 `npm install` 安装依赖。`` |

链接按显示文字判断边界；中文全角标点前后不额外加空格。

### 标点

- 中文正文默认全角标点；引号用直角 `「」`，嵌套用 `『』`（项目/地区规范可覆盖）
- 作品名用 `《》`；按钮、菜单、字段展示名用 `「」`；机器可读字段名用行内代码
- 省略号 `……`、破折号 `——`，不用三个句点或连续连字符
- 完整句式列表项统一句号，短语型可不加，同一列表保持一致
- 冒号后应确有解释、列举或引用

| 不推荐 | 推荐 |
| --- | --- |
| `点击“保存”按钮。` | `点击「保存」按钮。` |
| `应用程序接口( API )` | `应用程序接口（API）` |
| `参见「安装指南」。` | `参见《安装指南》。` |
| `正在加载...` | `正在加载……` |

### 数字、单位与日期

- 数字与半角单位符号之间加空格：`10 GB`、`200 ms`、`25 °C`
- 百分号、角度符号紧邻数字：`50%`、`90°`；温度 `°C` 与角度 `°` 不混淆
- 数值范围优先用 `至`：`3 至 5 天`
- 中文日期 `2026 年 9 月 29 日`；时间内部不加空格：`15:30`
- 负号、小数点、千位分隔符与数字之间不加空格；不擅自换算单位或增减小数位

### 段落换行

中文 Markdown 段落保持一段一行，不做硬换行（软换行在渲染时按空格处理，中英边界断行会多出或吞掉空格）。代码块、表格、标题、引用块、显式换行保持原样。展开硬换行后逐处复查拼接边界留白。

### 术语大小写（常见确定项）

`ID`、`HTTP`、`URL`、`JSON`、`API`、`AI`、`LLM`、`RAG`、`AIGC`、`JavaScript`、`TypeScript`、`Python`、`Node.js`、`GitHub`、`GitLab`、`PostgreSQL`、`gRPC`、`GraphQL`、`WebSocket`、`YAML`、`XML`、`JWT`、`OpenAI API`、`ChatGPT`。依赖语境需人工确认：`JS`、`H5`、`Postgres`、`OAuth`、`k8s`。

## 六、空泛表达与黑话

以下词语容易掩盖具体动作，仅在明确业务定义、正式术语、引用原文或用户要求时使用：

`赋能`、`抓手`、`闭环`、`沉淀`、`对齐`、`对标`、`拉通`、`打通`、`协同`、`联动`、`洞察`、`赛道`、`心智`、`调性`、`战役`、`链路`、`势能`、`兜底`、`落盘`、`收口`、`透传`

替换示例：

| 黑话 | 实际写法 |
| --- | --- |
| `赋能` | `提供`，或直接写提供的能力 |
| `抓手` | `关键措施` |
| `闭环` | `完整流程`，或列出开始、处理和完成条件 |
| `沉淀` | `形成`、`积累`、`保存` |
| `对齐` | `统一`、`确认一致` |
| `洞察` | `分析结论` |
| `兜底` | 写出失败后的具体保障机制 |
| `落盘` | `写入文件`、`保存到本地` |
| `透传` | `原样传给下游` |

依赖语境、不由检查器自动替换：`场景`、`生态`、`体系`、`路径`、`触点`、`卡点`、`布局`、`矩阵`、`颗粒度`、`复盘`、`梳理`、`输出`、`提炼`。

## 七、高频错词与语境词

确定错误：`阀值`→`阈值`、`布署`→`部署`、`反回`→`返回`、`回朔`→`回溯`、`做为`→`作为`、`embeding`→`embedding`、`提示工程学`→`提示工程`。

语境判断：

- `登录系统` / `登陆月球`
- `配置参数` / `配制溶液`
- `截至 4 月 12 日` / `截止日期`
- `启用功能` / `起用新人`
- `标识字段` / `在图中标示位置`
- `认证`确认身份 / `授权`授予权限

## 八、数量与逻辑表达

- `缩小了 3 倍` → `缩小到原来的 1/3` 或写明减少比例
- `从 20% 增长到 30%`：增加 10 个百分点，相对增长 50%
- `转化率提升了 5%`：确认是 5% 还是 5 个百分点
- `翻了 1 倍` → `变为原来的 2 倍`
- `不超过 100 以上` → `不超过 100`
- 修正表达时不得自行补充原文没有的基数、年份、期限或测量结果

## 九、受控中文技术写作

借鉴 ASD-STE100 受控语言思路（非其中文版、不表示认证合规），用于操作手册、安装部署、故障排查、运维 Runbook、安全警告和多步骤 API 流程。

### 六项核心原则

1. **保留事实**：不新增数字/能力/结论，不删除警告、限制、例外、单位、默认值
2. **一个概念一个首选术语**：不轮换同义词；首次出现缩写给全称
3. **一个步骤一个主要动作**：以明确动作开始，写清对象；顺序动作拆编号步骤
4. **条件和风险先于动作**：前置条件、警告放在动作之前；关键限制不放步骤末尾括号
5. **明确执行者、对象和结果**：区分系统自动行为与人工操作；不用无法定位的「该」「其」「上述」
6. **保持逻辑顺序**：按实际执行顺序；排查先给低风险、可逆、证据价值高的检查；原因、现象、操作、结果分开

### 操作步骤模板

1. 前置条件 → 2. 风险或限制 → 3. 编号操作步骤 → 4. 每步预期结果 → 5. 失败停止条件和恢复方式

### 故障排查模板

1. 可观察现象 → 2. 需收集的日志/状态/错误码 → 3. 按证据和风险排序检查 → 4. 每项检查的判断条件 → 5. 证据支持才给原因 → 6. 恢复操作、验证方式、停止条件

品牌文案、叙事文本、法律原文不机械应用；「可能原因」不改写成「确定原因」。

## 十、API 状态与错误文案

- 先确认状态在当前接口中的真实含义再选中文，不把一个英文词固定映射唯一中文
- 不修改状态码、枚举值、字段名和响应原文
- `Invalid` 不默认译 `非法`；`Unauthorized` 按原因写 `未登录`/`认证未通过`/`缺少认证信息`
- 参数说明写清：类型格式、是否必填、单位、默认值、允许范围、缺省行为、依赖互斥
- 错误文案顺序：发生了什么 → 哪个对象受影响 → 可能原因 → 可执行的恢复操作 → 仍失败时提供的诊断信息
